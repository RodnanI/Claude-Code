Ignoring files with .gitignore

Some files should never end up in history: passwords, gigabytes of downloaded libraries, logs, your computer's junk files. A small text file called .gitignore keeps them out.

What should never be committed

Secrets

.env files, API keys, passwords, private keys. Once pushed to GitHub, assume they are stolen.

Things you can regenerate

Downloaded libraries (node_modules/, venv/), build output (dist/, build/), caches (__pycache__/).

Personal junk

macOS .DS_Store, Windows Thumbs.db, editor folders like .idea/, and *.log files.

Huge files

Videos, datasets, zip archives. They bloat history forever, even after you delete them.

How it works

Create a file named exactly .gitignore (with the leading dot, no extension) in the top folder of your repository. Each line is a pattern. Git then pretends matching untracked files do not exist: they vanish from git status, and git add . skips them.

.gitignore
# secrets
.env

# dependencies and build output
node_modules/
dist/

# logs and OS junk
*.log
.DS_Store

Commit the .gitignore file itself, so everyone working on the project gets the same rules.

Pattern rules

PatternIgnores
secret.txtAnything named secret.txt, in any folder
*.logEvery file ending in .log, anywhere. * matches any characters except a slash.
build/Folders named build, and everything inside. The trailing slash means "folders only".
/buildOnly the build at the top of the repository, not src/build. A leading slash anchors the pattern.
docs/*.pdfPDFs directly inside the top-level docs folder. A slash in the middle also anchors the pattern.
**/temptemp at any depth. ** matches any number of folders.
!keep.logAn exception: do not ignore keep.log, even though *.log said so
# noteNothing. Lines starting with # are comments for humans.

Test the rules

Edit either box. The right column explains every decision, including files ignored only because a folder they sit in is ignored.

An exception cannot rescue a file inside a folder that is ignored as a whole. If logs/ is ignored, !logs/keep.log does nothing, because git never even looks inside logs. Ignore logs/* instead (the contents, not the folder), and the exception works. Try both in the tester.

Already committed? .gitignore will not help

.gitignore only affects files git is not tracking yet. If a file was already committed, adding it to .gitignore changes nothing: git keeps tracking it. Untrack it first:

$ echo ".env" >> .gitignore
$ git rm --cached .env
rm '.env'
$ git commit -m "Stop tracking .env"

--cached means "remove it from git, but leave the real file on my disk".

Removing it now does not remove it from history; anyone can still open the old commit. And bots scan GitHub for leaked keys within minutes. Revoke or rotate the key first: create a new one on that service and disable the old one. That is the actual fix. Scrubbing history is optional cleanup afterwards.

Do not write it from scratch

GitHub keeps ready-made templates for nearly every language and tool at github.com/github/gitignore, and offers them in a dropdown when you create a repository on the website. Start from one of those and add your own lines.

Practice

You add passwords.txt to .gitignore, but it was committed last week. What happens?

Right. Ignore rules only apply to untracked files. And if that file was ever pushed, change those passwords.
