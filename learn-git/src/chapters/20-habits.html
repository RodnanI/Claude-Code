Good habits and team workflows

The commands are the easy part. What separates a painless project from a miserable one is a handful of habits. None of them are hard, and all of them pay off.

Commit small, commit often

A commit should be one logical change: "Add search box", not "Monday's work". Small commits are easy to review, easy to revert and easy to understand later. Committing often means you always have a recent save point, which makes undoing cheap.

Write messages future you can use

Type a message and watch the signal. It checks the conventions most projects follow.

  • First line: a short summary in the command form, about 50 characters, no period. Test it by reading "If applied, this commit will fix crash when the cart is empty".
  • Need more room? Leave a blank line and explain why in as much detail as you like. From the terminal: git commit -m "Title" -m "Longer explanation".
  • Some teams use Conventional Commits prefixes: feat: add search, fix: handle empty cart, docs: update README. Copy whatever the project already does.

The GitHub flow

The simple workflow most teams use, and what this whole guide has been building towards:

  1. main always works. Nobody commits half-finished work to it directly.
  2. Every task gets a branch, created from an up-to-date main.
  3. Push early and open a pull request (a draft is fine) to get feedback.
  4. Review, then merge once the checks are green.
  5. Delete the branch and start the next task from a fresh main.

Rules that prevent disasters

  • Pull before you start working, and before you push. Fewer surprises, smaller conflicts.
  • Look before you commit: git status and git diff --staged catch the stray debug file.
  • Never commit secrets. Set up .gitignore on day one.
  • Never force-push a shared branch. On your own branch, prefer --force-with-lease, which refuses if someone else pushed in the meantime.
  • Read commands from the internet before running them, especially anything containing --force, reset --hard or clean.
  • Keep branches short-lived. Days, not months.

Things that bite people eventually

Line endings
Windows ends lines with two invisible characters, macOS and Linux with one. Mixed teams see whole files as "changed". Set core.autocrlf as shown in setup, or add a .gitattributes file containing * text=auto.
Big files
GitHub rejects files over 100 MB and warns above 50 MB. For large assets use Git LFS (git lfs track "*.psd"), or keep them out of git altogether.
Case-only renames
Renaming Readme.md to README.md confuses git on Windows and macOS. Use git mv Readme.md README.md.
Empty folders
Git only tracks files, so an empty folder is invisible to it. Put a placeholder file inside (often named .gitkeep) if the folder must exist.

Apps and buttons are fine

VS Code's Source Control panel, GitHub Desktop, JetBrains IDEs, lazygit, Fork, Sublime Merge: all excellent, and many professionals live in them. Now that you know the commands, every button makes sense: Stage is git add, Sync is pull and then push, Discard is git restore. Use whatever is fastest, and drop to the terminal when something looks off.

Which is the best commit message?

Right. Specific, short, in the command form, no period. You could find this commit a year from now.
