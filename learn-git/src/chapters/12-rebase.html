Rebase (optional, but you will hear about it)

Rebase is the other way to bring branches together. It rewrites your branch so it looks as if you had started from the latest main, giving a perfectly straight history. Powerful, occasionally dangerous, and not required for beginners.

Merge and rebase, side by side

Both tabs start from the same situation: main and feature both have new commits. Step through each and compare the final maps.

Merge shows the truth: two lines that joined. Rebase replays your commits one by one on top of main, producing a straight line. The faded grey stations are the originals.

Rebase creates new commits

This is the key fact. Compare the hashes before and after: they change. A commit's hash depends on its parent, so moving a commit onto a new parent creates a brand-new commit. The old ones still exist for a while (the reflog can find them), but no branch points at them anymore.

The golden rule

If you rebase commits that are already on GitHub and a teammate has pulled them, your history and theirs now disagree about what those commits are. The result is duplicated commits and very confused colleagues. Rebase only your own local work, or a feature branch nobody else uses.

If you rebase your own branch after pushing it, a normal push gets rejected (the histories no longer line up), and you need git push --force-with-lease. Fine on your own branch, a disaster on a shared one.

How to use it

# update your feature branch with the latest main
$ git switch feature
$ git rebase main

If a replayed commit conflicts, git pauses, just like a merge. Fix the file, then:

$ git add salsa.txt
$ git rebase --continue
# or give up and go back to how things were:
$ git rebase --abort

A very common everyday use is git pull --rebase: it puts your unpushed commits on top of what you just downloaded, instead of making a merge commit.

Interactive rebase: tidying up

git rebase -i HEAD~3 opens your last three commits in your editor as a to-do list. The word at the start of each line decides what happens to that commit:

git-rebase-todo
pick   a1b2c3d Add taco recipe
squash e4f5a6b Fix typo in tacos
reword 9c8d7e6 Add salsa to tacos

# pick   = keep the commit as it is
# reword = keep it, but edit its message
# squash = melt it into the commit above
# drop   = delete the commit entirely

Save and close, and git rewrites those commits accordingly. People use it to clean up messy "wip" commits before opening a pull request. The golden rule still applies. (The practice terminals do not simulate interactive rebase.)

So which should I use?

Honest answer: as a beginner, merge. It never rewrites anything, so it is hard to hurt yourself with it. Many teams pick one style per project, and GitHub can enforce it through the merge button (see the pull request stop). When a team asks you to rebase, you now know what that means and what to watch for.

Why do rebased commits get new hashes?

Right. Same changes, different parent, so a different commit. That is also why rebasing shared commits causes trouble.

Is it fine to rebase a branch your teammates are also working on?

Right. Rewriting shared history forces everyone else to untangle their copies.
