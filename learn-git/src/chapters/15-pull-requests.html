Pull requests

This is how teams really work together on GitHub. Nobody pushes straight to main. You push a branch and open a pull request: a proposal saying "please review these changes and merge them in".

What a pull request is

A pull request (PR) is a page on GitHub attached to a branch. It shows every commit and every changed line, has a discussion thread, runs automatic tests, and ends with a Merge button. The name comes from asking the maintainers to pull your changes in. GitLab calls the same thing a merge request.

Why not merge on your own computer and push? Because a pull request gives you:

  • Review: a teammate reads your change before it lands. Bugs get caught and knowledge spreads.
  • Automatic checks: tests run on every push, so a broken change shows a red X before it is merged.
  • A record: months later, the PR explains why a change was made, with the whole discussion attached.
  • A protected main: repositories can require a PR and an approval for every change to main.

The workflow

  1. Update main: git switch main, then git pull
  2. Branch: git switch -c add-tacos
  3. Work and commit, as many commits as you like
  4. Push the branch: git push -u origin add-tacos
  5. Open the pull request on GitHub
  6. Discuss, review, fix: push more commits to the same branch; the PR updates itself
  7. Merge once it is approved and the checks are green
  8. Clean up: delete the branch, then git switch main and git pull

Three ways to merge

GitHub's merge button has a dropdown with three options. Here is what each does to main on GitHub, for a pull request with two commits:

Merge commit
Keeps every commit, plus a merge commit. Complete, but busy.
Squash and merge
One commit per pull request. The most popular choice for tidy history; your "fix typo" commits never reach main.
Rebase and merge
Keeps every commit, in a straight line, without a merge commit.

Squashing creates a brand-new commit, so git on your computer does not recognize your branch as merged, and git branch -d add-tacos complains that it is not fully merged. If you know the PR was merged, git branch -D add-tacos is fine.

Writing a good pull request

  • Keep it small. A 50-line PR gets a careful review in ten minutes. A 2,000-line PR gets "looks good to me" and a hidden bug.
  • A title that says what it does: "Add taco recipe", not "Updates".
  • A description that says why, how to test it, and screenshots for anything visual.
  • Link the issue: Closes #12 in the description closes issue 12 automatically when the PR is merged.
  • Draft PRs (the arrow next to "Create pull request") mean "not ready, but have a look". Great for early feedback.

Reviewing someone else's

  • Open Files changed, and click the + beside any line to comment on it.
  • Use suggestions for small fixes; the author can apply them with a click.
  • Finish with Comment, Approve or Request changes.
  • Be specific and kind. Comment on the code, not the person. Questions ("what happens if the list is empty?") land better than verdicts.
