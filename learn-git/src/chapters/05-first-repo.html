Your first repository

Enough theory. Let's make a project, put it under git and save the first snapshot. This is the loop you will repeat for the rest of your life: change something, stage it, commit it.

Step 1: a folder

A repository starts life as a completely normal folder:

$ mkdir recipes
$ cd recipes

Step 2: git init

$ git init
Initialized empty Git repository in /home/you/recipes/.git/

That is all it takes. Git created a hidden folder called .git inside recipes. That hidden folder is the repository: every commit, branch and setting lives there. Your own files stay exactly where they are.

$ ls -a
./   ../   .git/

Never edit or delete the .git folder by hand. Deleting it deletes the entire history of the project. Your current files survive, but every commit is gone.

Do not run git init in your home folder or on your Desktop, or git will try to track everything in there. Always cd into a project folder first. If it already happened, deleting that stray .git folder (only that one) fixes it.

Step 3: make a file

Create a file any way you like: in VS Code, in Notepad, or straight from the terminal:

$ echo "Pancakes: flour, eggs, milk" > pancakes.txt

Step 4: git status, your best friend

git status tells you what git sees right now. Run it constantly. It costs nothing and it explains itself. Hover the parts of its answer:

On branch main No commits yet Untracked files: (use "git add <file>..." to include in what will be committed) pancakes.txt nothing added to commit but untracked files present (use "git add" to track)

Hover or tap each colored part of the output.

Step 5: git add

Committing is a two-step dance. First you pick which changes go into the next snapshot. That is called staging, and git add does it:

$ git add pancakes.txt
$ git status
On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
        new file:   pancakes.txt

In a real terminal that line turns green: the file is staged and ready for the snapshot. Why two steps? That is the whole next stop.

Step 6: git commit

$ git commit -m "Add pancake recipe"
[main (root-commit) dc90184] Add pancake recipe
 1 file changed, 1 insertion(+)
 create mode 100644 pancakes.txt

Your first commit. Reading the reply: it went onto the branch main, it is the root (very first) commit, its ID starts with dc90184, and it added one file containing one line. The text after -m is the commit message.

Without -m, git opens your text editor and waits for you to write a message, save and close it. If it opened Vim and you feel trapped: press Esc, type :wq, press Enter.

Step 7: look at your history

$ git log
commit dc90184a7a70b49d29b3a36fb05a03298be8832c (HEAD -> main)
Author: Ada Lovelace <ada@example.com>
Date:   Mon Sep 14 09:15:53 2026 +0000

    Add pancake recipe

A decent commit message

Future you will read these messages when something breaks. Make them useful:

  • Say specifically what changed: "Add pancake recipe", not "update".
  • Write it as a command, the way git's own messages read: "Add", "Fix", "Remove", not "Added" or "Adding".
  • Keep the first line short, around 50 characters. More detail can go in a second paragraph.

The Good habits stop has a checker that grades your messages as you type.

You just ran git add notes.txt. Is notes.txt saved in the history yet?

Right. git add puts the change in the staging area. git commit is what records a snapshot. Pushing is a separate, later step that uploads commits.

What does git init create?

Right. It turns the folder into a repository by adding .git. Nothing is saved until your first commit, and nothing goes online.
