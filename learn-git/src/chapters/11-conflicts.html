Merge conflicts, calmly

A conflict is not an error, and nothing is broken. It is git saying: two people changed the same lines in different ways, and I refuse to guess which one is right. You decide.

When they happen

You made the salsa mild on main. A friend made it hot on a branch called spicy. You both edited the same line. When you merge, git sees two opinions about one line and stops:

$ git merge spicy
Auto-merging salsa.txt
CONFLICT (content): Merge conflict in salsa.txt
Automatic merge failed; fix conflicts and then commit the result.

The merge is now paused halfway. git status lists conflicted files as both modified. Everything that merged cleanly is already staged.

Reading the conflict markers

Git writes both versions into the file, fenced off by conflict markers. Hover the parts:

Salsa - 4 ripe tomatoes - 1 onion <<<<<<< HEAD - half a jalapeno (mild) ======= - 3 jalapenos (hot!) >>>>>>> spicy - juice of 1 lime

Hover or tap the marked lines.

Notice line 2 already says "4 ripe tomatoes". Only the spicy branch changed that line, so git merged it without asking. Only the line both sides touched is in conflict.

Fixing it in three steps

  1. Edit the file into its final form. Keep your version, theirs, both, or write something new. Then delete all three marker lines. The file should read like a normal file again.
  2. Stage it with git add salsa.txt. That is how you tell git "this one is resolved".
  3. Finish the merge with git commit. Git already prepared the message.

Editors like VS Code turn step 1 into a click: they highlight each conflict and put buttons above it. This mock works the same way. Resolve both files:

Changed your mind? Abort

$ git merge --abort

Puts everything back exactly the way it was before you ran git merge. Always available while a merge is paused. No harm done.

Now for real

The same conflict in a terminal. You will fix the file in the built-in editor, just as you would with nano or VS Code.

Fewer, smaller conflicts

  • Merge or pull often. The longer two branches drift apart, the bigger the eventual conflict.
  • Keep branches small and short. A two-day branch rarely conflicts badly. A two-month branch always does.
  • Talk to each other. If two people need to rework the same file, coordinate first.
  • Do not reformat whole files in the same commit as real changes. Re-indenting every line makes every line conflict.

Git does not check whether you actually removed the markers. If you git add a file that still contains <<<<<<< lines, they get committed, and your program or document breaks. Always look at the file before adding it.

In a conflict, the lines between <<<<<<< HEAD and ======= are...

Right. HEAD is where you are. The incoming version sits between ======= and >>>>>>>.

You fixed the file and removed the markers. What next?

Right. Adding marks it resolved; committing completes the paused merge.
