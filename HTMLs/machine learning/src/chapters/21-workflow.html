The ML project workflow

Training the model is maybe a fifth of a real project. The rest is framing the problem, wrangling data, evaluating honestly, shipping, and keeping it working.

1. Frame the problem

The most expensive mistakes happen before any code. Answer these in writing:

  • What decision or action will the prediction change? Who uses it, and when?
  • What is the target, exactly? "Churn" meaning cancels within 30 days? 90? Precise definitions prevent months of confusion.
  • What metric reflects success, and what do false positives and false negatives each cost?
  • What would a non-ML solution achieve? That is your baseline to beat.
  • What data is available at prediction time? (Leakage prevention starts here.)

2 to 4. Data, exploration, baseline

Gather data, and if you need labels, write labeling guidelines and measure how often two labelers agree: if humans disagree 20% of the time, no model will be 99% accurate. Explore distributions, missing values and relationships, and hunt for suspiciously predictive features. Then build the simplest possible end-to-end baseline, from raw data to a metric, so everything later is a measured improvement.

5. Iterate with error analysis

Do not just stare at the aggregate score. Pull 50 to 100 examples the model gets wrong and categorize them by hand. You will find label errors, missing features, confusing classes, and data quirks. This single habit separates effective practitioners from people who try random architectures. Track every experiment (parameters, data version, code version, metrics) so you can reproduce and compare.

6. Evaluate like a skeptic

  • Report on the untouched test set once, at the end.
  • Break metrics down by slices: regions, device types, customer segments, demographic groups. A great average can hide a disaster in one slice.
  • Offline metrics are a proxy. The real test is an online experiment (A/B test) measuring the business outcome.

7. Deploy

ModeHowGood for
BatchScore all records on a schedule, write results to a tableDaily churn scores, weekly forecasts, lead ranking
Real timeModel behind an API; predict per request in millisecondsFraud checks at payment, recommendations, search ranking
On deviceCompressed model running on the phone or edge hardwareKeyboard prediction, camera effects, offline use

Package preprocessing and model together (a scikit-learn Pipeline or an exported graph) so training and serving cannot drift apart, a bug called training-serving skew.

8. Monitor, because the world moves

  • Data drift: input distributions change (new customer types, a sensor replaced, a UI redesign).
  • Concept drift: the relationship itself changes (fraudsters adapt, tastes shift, a pandemic hits).
  • Feedback loops: the model's own decisions shape future training data (a recommender only learns about what it chose to show).

Log inputs and predictions, compare live distributions with training ones, track performance as labels arrive, and schedule or trigger retraining.

In code

# train.py
import joblib
from sklearn.model_selection import cross_val_score
from lightgbm import LGBMClassifier
from sklearn.pipeline import Pipeline

pipe = Pipeline([("prep", prep), ("model", LGBMClassifier(n_estimators=400, learning_rate=0.05))])
print(cross_val_score(pipe, X_train, y_train, cv=5, scoring="roc_auc").mean())
pipe.fit(X_train, y_train)
joblib.dump(pipe, "model.joblib")          # preprocessing + model in one artifact

# serve.py  (run with: uvicorn serve:app)
import joblib, pandas as pd
from fastapi import FastAPI
app = FastAPI()
pipe = joblib.load("model.joblib")

@app.post("/predict")
def predict(record: dict):
    p = pipe.predict_proba(pd.DataFrame([record]))[0, 1]
    return {"churn_probability": float(p)}

A model performs well offline but poorly in production. Preprocessing was reimplemented separately in the serving code. What is the likely culprit?

Two implementations of the same transformation rarely match perfectly. Ship preprocessing and model as one artifact.

Which habit most improves a model in practice?

Error analysis reveals label problems, missing features and data issues that no amount of blind tuning will fix.

A fraud model's precision slowly degrades over six months though nothing in the code changed. What is most likely?

Adversaries adapt. Monitoring and periodic retraining on recent data are essential for fraud and similar domains.
