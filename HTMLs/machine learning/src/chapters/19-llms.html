Large language models

A transformer trained to predict the next token, on a large fraction of the written internet, then taught to be a helpful assistant. Here is what is actually going on, and how people use them at work.

Next-token prediction

A large language model (LLM) is a decoder-only transformer (chapter 18) whose output layer is a softmax over its whole vocabulary, often 50,000 to 200,000 tokens. Given the text so far, it outputs a probability for every possible next token. To write a response it picks one token, appends it, and runs again. Every word you read from a chatbot was produced this way, one token at a time.

The training objective sounds almost trivially simple: predict the next token, measured by cross-entropy (chapter 06). But to predict text well across billions of documents, a model has to pick up grammar, facts, styles, the structure of code, and patterns of reasoning. That compression of the world's text into weights is what makes the result useful.

Tokens

Models do not see characters or words but tokens, produced by algorithms like byte-pair encoding that merge frequent character sequences. Common words are one token; rare words split into pieces: "unbelievably" might become un believ ably. In English a token averages roughly three quarters of a word. Tokens are the unit of everything practical: context window size, speed and price. They also explain some odd failures, like miscounting the letters in a word the model never sees letter by letter.

Choosing the next token

The model outputs probabilities; a decoding strategy turns them into a choice. Always taking the most likely token (greedy decoding) is repetitive and bland. Sampling adds variety, controlled by a few knobs you will see in every LLM API:

  • Temperature divides the scores before the softmax. Below 1 sharpens the distribution (more predictable), above 1 flattens it (more surprising, eventually incoherent).
  • Top-k keeps only the k most likely tokens.
  • Top-p (nucleus sampling) keeps the smallest set of tokens whose probabilities add up to p.

From text predictor to assistant

  1. Pretraining: next-token prediction on trillions of tokens of text and code. This is where nearly all knowledge and capability comes from, and nearly all the compute cost. The result, a base model, continues text but does not follow instructions reliably.
  2. Supervised fine-tuning: continued training on curated examples of instructions paired with high-quality responses. The model learns the format and behavior of an assistant.
  3. Preference tuning: people (or AI feedback guided by written principles) compare pairs of responses; the model is optimized toward the preferred ones. RLHF uses reinforcement learning (chapter 20) for this; methods like DPO optimize preferences directly.

Using LLMs in real work

Prompting

Say what you want

Clear instructions, relevant context, examples of the desired output (few-shot), and a specified format. Cheapest lever; try it first.

RAG

Retrieval-augmented generation

Embed your documents, retrieve the most relevant chunks for each question (k-NN, chapter 09), and put them in the prompt. Grounds answers in your data and reduces made-up facts.

Fine-tuning

Adjust the weights

Train further on your examples to lock in a style, format or narrow skill. Parameter-efficient methods like LoRA train small add-on matrices instead of the whole model.

Agents

Tools and loops

Let the model call functions (search, code execution, databases) and iterate on the results. Powerful, and harder to test and secure.

  • Hallucination: fluent, confident, wrong. The model generates plausible text, not verified truth. Ground it with retrieval and check important outputs.
  • Knowledge cutoff: it only knows what was in its training data unless you provide more in the context.
  • Prompt injection: instructions hidden in documents or web pages the model reads can hijack its behavior. Treat model output that triggers actions as untrusted.
  • Evaluation is hard: build a test set of real inputs with expected outputs (an "eval") before you change prompts or models, exactly like a validation set.

In code

from transformers import pipeline

gen = pipeline("text-generation", model="gpt2")      # small, old, but runs anywhere
out = gen("The best way to learn machine learning is",
          max_new_tokens=30, do_sample=True,
          temperature=0.7, top_k=50, top_p=0.9)
print(out[0]["generated_text"])
from sentence_transformers import SentenceTransformer
import numpy as np

docs = ["Refunds are processed within 5 business days.",
        "Our office is closed on public holidays.",
        "Premium members get free shipping."]
enc = SentenceTransformer("all-MiniLM-L6-v2")
D = enc.encode(docs, normalize_embeddings=True)

q = enc.encode(["How long does a refund take?"], normalize_embeddings=True)
best = np.argsort(-(D @ q.T).ravel())[:2]            # cosine similarity, top 2
context = "\n".join(docs[i] for i in best)
prompt = f"Answer using only this context:\n{context}\n\nQuestion: How long does a refund take?"
# send `prompt` to the LLM of your choice

What is an LLM trained to do during pretraining?

Pretraining is self-supervised next-token prediction. Instruction following comes later from fine-tuning and preference tuning.

You need consistent, factual extraction of fields from invoices. How should you set temperature?

Low temperature concentrates probability on the most likely tokens, giving more deterministic output. High temperature is for creative variety.

Your chatbot must answer questions about your company's internal policies, which change monthly. What is usually the best first approach?

RAG puts the latest relevant text into the prompt at question time, so updates only require re-indexing documents, not retraining.
