Merging and merge conflicts

Merging brings the work from one branch into another. Most merges happen automatically in a second. Sometimes Git hits a question it cannot answer on its own, a conflict, and asks you. That is not an error; it is a question.

You merge into the branch you are on

The rule people mix up: git merge feature brings feature into your current branch. So first go to the branch that should receive the work, then merge:

git switch main
git merge dark-mode

Two kinds of merge

You do not choose between these; Git picks automatically. (If you always want a merge commit, git merge --no-ff branch forces one.) For a real merge commit Git needs a message and may open your editor with one prewritten, like "Merge branch 'dark-mode'". Save and close to finish.

Practise: one easy merge, one conflict

Anatomy of a conflict

A conflict happens when both branches changed the same lines in different ways. Git writes both versions into the file, fenced by conflict markers:

body {
<<<<<<< HEAD
  background: orange;
=======
  background: palegreen;
>>>>>>> new-colors
  font-family: sans-serif;
}
  • Between <<<<<<< HEAD and =======: your version, from the branch you are on ("current").
  • Between ======= and >>>>>>> new-colors: the version being merged in ("incoming").
  • Everything outside the markers merged cleanly already.

Resolving a conflict, step by step

  1. git status lists every conflicted file under "Unmerged paths".
  2. Open each one. Search for <<<<<<<. VS Code highlights conflicts and offers clickable Accept Current Change, Accept Incoming Change and Accept Both Changes links above each one.
  3. Edit the text into what it should finally be. Keep one side, the other, both, or write something new. Delete every marker line.
  4. Save, then mark the file as resolved: git add style.css
  5. When all files are resolved, finish with git commit (Git suggests the message).

Panicking halfway through? This puts everything back to how it was before the merge:

git merge --abort

Careful

Git lets you git add a file that still contains markers. It will happily commit a broken file. Always search for <<<<<<< before adding.

Fewer conflicts, less pain

  • Merge main into your branch often, so differences stay small.
  • Keep branches short-lived: days, not months.
  • Do not reformat a whole file in the same branch as a real change; that touches every line.
  • Talk to your team when two people need the same file.

You want the work from branch fix to end up on main. What do you run?

  • git switch fix, then git merge main
  • git switch main, then git merge fix
  • git merge main fix

Merge brings the named branch into the branch you are standing on.

What does the section between ======= and >>>>>>> new-colors contain?

  • Your version
  • The version from new-colors, the branch being merged in
  • The version from before both changes

Top half is HEAD (you), bottom half is the incoming branch.

You resolved the conflict in the file. What tells Git it is resolved?

  • Saving the file
  • git add on that file
  • git merge --abort

git add marks the conflict as resolved; then git commit finishes the merge.
