Pull requests

A pull request (PR) says: "I made changes on a branch. Please look at them, and if they are good, merge them into main." It is where review, discussion and automatic checks happen before anything touches main.

Why teams (and even solo developers) use them

  • A second pair of eyes. A teammate reads the change before it lands. Bugs get caught while they are cheap.
  • Automatic checks. Tests and builds run on every PR and show a green or red mark.
  • A record of why. Months later, the PR page still explains what changed and why, with the whole discussion.
  • main stays clean. Nothing reaches it without passing through a PR.

Squash is the most common choice on busy projects: one PR becomes one commit on main, however messy the branch was. Whatever the project uses, the result on main contains your change.

Reviewing someone else's pull request

  1. Open the PR and go to the Files changed tab.
  2. Hover a line and click the + that appears to comment on it. You can even suggest an exact replacement with the "suggestion" button, which the author can accept with one click.
  3. Click Review changes and pick Comment, Approve or Request changes.

Want to run their branch on your PC? With the GitHub CLI it is one command (12 being the PR number):

gh pr checkout 12

Keeping your PR up to date

If main moves on while your PR waits, bring the new main into your branch and push again. The PR updates by itself:

git switch main
git pull
git switch fix-typo
git merge main
git push

GitHub also shows an Update branch button on the PR page that does the same thing on the website.

Pull requests from the terminal

# open a PR for the current branch, title and text taken from your commits
gh pr create --fill
# see its status, or open it in the browser
gh pr status
gh pr view --web
# merge it (once allowed) and delete the branch
gh pr merge --squash --delete-branch

Good pull request manners

  • One topic per PR. Small PRs get reviewed fast; huge ones get skimmed or ignored.
  • Title a stranger understands. Description: what, why, and how to test it. Screenshots for visual changes.
  • Link the issue: Closes #3 closes it automatically on merge.
  • Not finished but want feedback? Open a draft pull request.
  • Review comments are about the code, not about you. Answer each one, push fixes, say thanks.

A reviewer requested changes on your PR. What do you do?

  • Close it and open a new PR
  • Commit the fixes on the same branch and push; the PR updates itself
  • Merge anyway

A PR follows its branch. New commits pushed to the branch appear in the PR automatically.

In "base: main ← compare: fix-typo", which branch receives the changes?

  • main
  • fix-typo
  • Both

base is the destination, compare is your branch.

After your PR was merged on GitHub, what should you do on your PC?

  • Nothing, your PC updates automatically
  • git switch main, git pull, then git branch -d fix-typo
  • git push --force

GitHub does not touch your PC. Pull the merged main down, then delete the finished branch.
