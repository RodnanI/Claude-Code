What Git and GitHub actually are

Git is a time machine for a folder. GitHub is a website where those time machines live online, so people can back them up, share them, and work on them together. Two different things with confusingly similar names.

The problem Git solves

Everybody has done this. You are working on something important and you do not want to lose a good version, so you make copies:

With Git you keep working in normal files. Whenever you reach a good point, you tell Git to take a snapshot of the whole folder. That snapshot is called a commit. Each commit records:

  • exactly what every file looked like at that moment,
  • a short message you write ("Rewrite intro"),
  • who made it and when,
  • a unique ID, so you can point at it later.

With that, Git can show you what changed between any two commits, bring back any old version, and let you try risky ideas on a separate line of work (a branch) without touching the version that works.

Think of it like

Save points in a video game. You save before the boss fight; if the fight goes badly, you reload. Commits are save points for your project, except you keep all of them forever, each with a label saying what happened.

What Git is not

  • Not a backup on its own. Git stores its history inside your project folder. If the disk dies, the history dies with it. The copy on GitHub is what protects you.
  • Not only for code. Websites, notes, recipes, config files, books written in plain text: anything made of text files works beautifully. Large binary files (videos, Photoshop files, Word documents) can be stored, but Git cannot show you what changed inside them.
  • Not GitHub. Git runs on your PC and works fully offline. Which brings us to...

The terminal, minus the fear

The terminal is a window where you type instructions instead of clicking. It looks old-fashioned, but it only does what you already do with the mouse: open folders, make files, run programs. Fifteen minutes here makes every other stop easier.

Terminal, shell, PowerShell... what are all these words?

  • The terminal is the window itself.
  • The shell is the program inside that window which reads your commands and runs them.
  • PowerShell is the shell built into Windows 10 and 11. This guide uses it everywhere.
  • Command Prompt (cmd) is the older Windows shell. It works with Git too, but its commands differ.
  • Git Bash arrives with Git (next stop). It is a Linux-style shell. Handy for following Linux tutorials, not required here.

On Win 11 the window app is called Windows Terminal and it opens PowerShell by default. It has tabs, so you can have several terminals side by side.

On Win 10 PowerShell opens in a plain blue or black console window. That is fine, but installing Windows Terminal (free, from the Microsoft Store) gives you tabs, better copy and paste and nicer fonts. Recommended, not required.

In Windows Terminal, Ctrl + V pastes, and Ctrl + C copies when text is selected. Right-click also pastes.

Careful

Pasting several lines runs all of them, one after another. And never paste commands from a random website unless you understand what they do. Anything that downloads and runs a script in one go deserves extra suspicion.

Reading error messages

Red text is not a disaster. It is the terminal telling you what went wrong, usually in the first line. The two you will meet most:

git : The term 'git' is not recognized as the name of a cmdlet, function, script file, or operable program.

Meaning: PowerShell cannot find a program with that name. Either a typo, or the program is not installed, or it was installed after this terminal window was opened (close it and open a new one).

cd : Cannot find path 'C:\Users\you\Docs' because it does not exist.

Meaning: no folder with that name here. Check the spelling, check where you are with pwd, list what is here with ls, and let Tab type names for you.

Names with spaces

A space separates words in a command, so a folder like Program Files must be wrapped in quotes: cd 'C:\Program Files'. Easiest habit: never put spaces in names of project folders and files. Use dashes: my-site.

Telling Git who you are

Every commit is stamped with a name and an email address. Git refuses to commit until it knows them. You set them once per PC, together with a few settings that make Git friendlier.

Build your setup commands

Fill in the form. The box underneath updates as you type; copy it and paste it into PowerShell. When these commands succeed they print nothing at all, which is normal.

What each line does

user.name and user.email
The author stamped on every commit you make. GitHub uses the email to link commits to your account and show your profile picture next to them.
init.defaultBranch main
New repositories start with a branch called main, the same name GitHub uses. Without it, Git says master and you get a mismatch later.
core.editor
Sometimes Git needs a longer text from you, for example a merge message, and opens an editor. This picks which one. code --wait makes Git wait until you close the VS Code tab.
pull.rebase false
Tells git pull to merge (the beginner-friendly behaviour this guide uses) and silences a warning that newer Git versions print otherwise.

What --global means

--global saves the setting for your Windows user, for every repository. It lands in a plain text file, C:\Users\you\.gitconfig. Without --global, a setting applies only to the repository you are standing in, which is how you would use a different email for work projects.

Look at the file directly if you are curious:

notepad $HOME\.gitconfig

Keeping your email private

Commits in public repositories are public, including the email inside them. If you would rather not publish your real address, GitHub gives you a private stand-in: on github.com open Settings → Emails, tick Keep my email addresses private, and copy the address shown there. It looks like this:

12345678+yourname@users.noreply.github.com

Use that as your user.email. You can come back to this after you create your account in Stop 11.

About that editor

When you run git commit without -m "message", or finish a merge, Git opens your editor with a text file and waits. You type the message, save, and close the tab or window. Only then does Git continue. If the terminal seems frozen after a Git command, look for an editor window waiting for you.

Windows 11 and Notepad

The Windows 11 Notepad opens files as tabs. If a Notepad window is already open, the file may open as a tab there and Git can stop waiting immediately, then complain: "Aborting commit due to empty commit message". If that happens, close Notepad completely and try again, or switch to VS Code.

Trapped in Vim?

If a strange full-screen editor appears in the terminal with ~ symbols down the left, that is Vim. Press Esc, type :q! and press Enter to leave without saving. (To save and continue instead: Esc, :wq, Enter.) Then set a friendlier editor with the form above.

The three places your work lives

This is the most important idea in Git. Every command you will learn moves changes between three places. Understand these three and the rest is details.

1. The working folder

Your actual files, exactly as File Explorer and your editor see them. This is where you work. Git watches this folder and notices every change, but watching is all it does. Nothing here is saved in Git's history yet.

2. The staging area

A waiting room for your next commit. git add index.html takes a copy of index.html as it is right now and puts it in the waiting room. You can add several files, one at a time, until the waiting room holds exactly what you want to save. Git's official name for it is the index; people also say "stage".

3. The repository

git commit takes everything in the staging area and saves it as one permanent snapshot, a commit. Commits are stored in a hidden folder called .git inside your project. That folder is the repository: the whole history lives there.

Think of it like

A group photo. People wander around the room (working folder). You call some of them up onto the stage (git add). Click: the photo (commit) shows exactly who was on the stage at that moment. The people still wandering around are not in the picture, and the picture never changes afterwards, even if someone on it changes their haircut.

Try it: move changes between the areas

Click the buttons in any order. Edit a file twice before adding it, add only one file, commit with nothing staged: see what happens and read the explanation below the boxes.

Why not just save everything automatically?

Because you often do two unrelated things at once. Say you fixed a typo on the homepage and started a half-finished new page. With staging, you add only the typo fix and commit it as "Fix typo". The half-finished page stays out of that commit. Clean, separate commits make history readable and make it possible to undo one change without undoing the other.

(And yes, when you just want everything, git add . stages the whole folder in one go.)

The hidden .git folder

The .git folder is hidden on purpose. You will never need to open it, but it helps to know it is there. To see hidden items in File Explorer:

Win 11 In File Explorer, click View → Show → Hidden items. While you are there, also tick File name extensions; it saves you from mistakes like a file secretly called .gitignore.txt.

Careful

Deleting .git deletes the entire history (your current files stay). Never edit anything inside it by hand, and never copy a project into another project's folder together with its .git.

You edit style.css, run git add style.css, then edit style.css again and commit. What goes into the commit?

  • The latest version, with both edits
  • The version from the moment you ran git add
  • Nothing, because the file changed again

git add copies the file as it is at that moment. The second edit is still only in the working folder. Run git add again to include it.

Where does Git keep all commits?

  • In the hidden .git folder inside the project

The repository is the .git folder. GitHub only has a copy once you push.

  • Uploading files
  • Choosing exactly which changes go into the next commit

What each command did

git init: start tracking this folder

Initialized empty Git repository in C:/Users/you/my-site/.git/

Creates the hidden .git folder. Your files are untouched. The forward slashes in the path are normal: Git comes from the Linux world and prints paths that way. Run git init once per project, never inside a folder that is already a repository.

git status: what is going on?

The command you will type more than any other. Read it top to bottom: which branch you are on, what is staged (green), what is changed but not staged (red), and what is untracked (red). It even tells you which command to run next, in brackets. When in doubt, git status.

git add: put changes in the staging area

Silent when it works. git add index.html stages one file, git add . stages everything in the folder, git add *.css stages all CSS files.

"LF will be replaced by CRLF"

On Windows, git add sometimes prints a warning about LF and CRLF. It is harmless: Git is telling you it will convert invisible line-ending characters. Stop 16 explains, with a demo.

git commit -m "message": save the snapshot

[main (root-commit) 3f9a2c1] First version of my site
 2 files changed, 6 insertions(+)
 create mode 100644 index.html
 create mode 100644 style.css
  • main: the branch the commit went on.
  • root-commit: the very first commit of the repository; it has no parent.
  • 3f9a2c1: the start of the new commit's unique ID.
  • "insertions" and "deletions" count changed lines. "create mode 100644" is file permission trivia you can ignore.

git log: the history

commit 3f9a2c1e8b7d6a5f4e3d2c1b0a9f8e7d6c5b4a39 (HEAD -> main)

Newest commit first. If the output is long, Git shows it one screen at a time with a : at the bottom. That is the pager: Space scrolls, q quits. The terminal is not frozen; it is waiting for you.

Writing good commit messages

Future you will read these when something breaks. A good message is a short summary (roughly 50 characters) written as a command, saying what the commit does:

WeakBetter
changesAdd contact form to homepage
fixed stuffFix broken link in footer
asdfMake header text readable on phones
updated index.html and style.css and the logo andThree separate commits, one per change

Commit whenever you finish one small, complete step you could describe in one sentence. Many small commits beat one giant "did everything" commit.

  • Close the window, it crashed
  • Press q to leave the pager
  • Press Ctrl + S

Long output opens in a pager. q quits and gives you the prompt back.

What order builds a commit?

  • git commit, then git add
  • edit files, git add, git commit
  • git init before every commit

Edit, stage what you want with git add, then save it with git commit. git init happens once per project.

Which commit message is best?

  • update
  • Fix typo in homepage heading
  • I changed some things in the files today because they were wrong

Short, specific, and phrased as what the commit does.

History is only useful if you can read it. Three commands do almost all of the looking back: git log lists commits, git show opens one, and git diff compares versions.

How to read a diff

A diff shows exactly which lines changed. It looks cryptic until you know the four parts:

diff --git a/about.html b/about.html
--- a/about.html
+++ b/about.html
@@ -1,2 +1,2 @@
 <h1>About me</h1>
-<p>I am learning Git.</p>
+<p>I am learning Git and GitHub.</p>
  1. diff --git names the file being compared.
  2. --- is the old version ("a"), +++ the new one ("b").
  3. @@ -1,2 +1,2 @@ says where: starting at line 1, 2 lines in the old version and 2 lines in the new.
  4. Lines starting with - (red) were removed, + (green) were added, a space means unchanged context. A changed line shows up as one removed plus one added.

Which diff compares what?

This is why git diff goes quiet after you git add: the working folder and the staging area match again. The change did not disappear; it moved one box to the right. git diff --staged shows it.

Naming commits

Many commands need you to point at a commit. You have several ways:

NameMeans
3f9a2c1The commit's ID. The first 7 characters are enough (copy them from git log --oneline).
HEADThe commit you are on right now.
HEAD~1, HEAD~2One, two commits before HEAD.
mainThe newest commit on the branch main.
main~3Three commits before the tip of main.

Why ~ and not ^

Tutorials sometimes write HEAD^. In Command Prompt the ^ character is special and gets swallowed, so HEAD~1 is the safer habit on Windows. It works everywhere.

Peek at an old version without changing anything

Print a file exactly as it was a few commits ago:

git show HEAD~2:index.html

Or bring back the old version of one file into your working folder (it shows up as a normal change you can commit, or undo):

git restore --source HEAD~2 index.html

The pager, once more

Long output (log, diff, show) opens in a scrollable viewer. Keys: Space next page, ↑ ↓ scroll, / then a word to search, q quit. If you would rather get plain output for one command, add --no-pager right after git:

git --no-pager log --oneline

You staged a change and now git diff prints nothing. Why?

  • The change was lost
  • git diff only shows unstaged changes; use git diff --staged
  • Git needs a restart

After git add, the working folder matches the staging area, so there is no unstaged difference left to show.

In a diff, what does a line starting with + mean?

  • A line that was added
  • A line that got longer
  • An important line

+ added, - removed. A modified line shows as one of each.

What is HEAD~1?

  • The first commit ever
  • The commit right before the current one
  • The next commit

HEAD is where you are; ~1 steps back one commit.

Undoing mistakes

Once something is committed, Git almost never truly loses it. The skill is not avoiding mistakes; it is picking the right undo for the mistake you made.

The one rule

Before pushing vs after pushing

Not pushed yet: the commits exist only on your PC, so you may rewrite them (amend, reset). Already pushed: other people may have them, so never rewrite. Add a new commit that undoes the old one (revert). Rewriting shared history is how teammates lose work.

Practise the common undos

The undo finder

Answer a question or two and get the exact command, with a warning label about how risky it is.

The undo commands, explained

git restore file: throw away unstaged edits

Puts the file back to how it is in the staging area (which, if you did not stage anything, equals the last commit). The edits are gone for good. They do not go to the Recycle Bin, because Git never saved them.

git restore --staged file: unstage

The opposite of git add. The change leaves the staging area but stays in your file. Completely safe.

git commit --amend: fix the last commit

Replaces the last commit with a new one containing whatever is staged now, plus a new message if you give one. Perfect for typos and forgotten files. It creates a new commit ID, which is exactly why you must not amend commits you already pushed.

# forgot a file:
git add forgotten.css
git commit --amend --no-edit

git revert: undo a commit by adding its opposite

Looks at what a commit changed and creates a new commit that changes it back. History stays intact (both commits are visible), which makes it the safe choice for anything already on GitHub.

git reset: move the branch backwards

Moves your branch to an earlier commit, as if later commits never happened. It has three strengths:

CommandBranch moves backStaging areaYour filesUse it to
git reset --soft HEAD~1YesKeeps the changes, stagedUntouchedRedo the last commit differently
git reset HEAD~1 (mixed, the default)YesEmptiedUntouched, changes still thereUn-commit and re-pick what to stage
git reset --hard HEAD~1YesEmptiedReset too: uncommitted work is deletedThrow everything away, for real

Careful with --hard

git reset --hard is one of the very few Git commands that destroys work you cannot get back: uncommitted changes. Run git status first and read it. The commits it removes can still be rescued for a while with the reflog (Stop 15); uncommitted edits cannot.

Old commands you will see online

Git added git restore and git switch in 2019 because the older git checkout did too many unrelated jobs. Older tutorials use the old forms. They still work:

Old wayNew way
git checkout -- filegit restore file
git reset HEAD filegit restore --staged file
git checkout branchgit switch branch
git checkout -b branchgit switch -c branch

Habits that make undo easy

  • Commit often. Committed work is recoverable almost forever. Uncommitted work is one bad command from gone.
  • Read git status before anything destructive.
  • Before an experiment, make a branch (next stop). If it fails, delete the branch.

You pushed a commit that broke the site. Teammates have already pulled it. What do you do?

  • git reset --hard HEAD~1, then push
  • git revert the commit, then push
  • git commit --amend

Pushed history is shared. git revert adds a fixing commit instead of rewriting history under your teammates' feet.

You staged passwords.txt by accident. How do you unstage it but keep the file?

  • git restore passwords.txt
  • git restore --staged passwords.txt
  • git reset --hard

--staged only touches the staging area. Without it, git restore works on your file instead.

Which command can delete work that is gone for good?

  • git revert
  • git restore --staged
  • git reset --hard

It overwrites your files, and uncommitted changes were never saved anywhere.

Branches

A branch sounds big, but it is a tiny thing: a movable name tag pointing at a commit. Creating one is instant and free. Everyone uses them, all day, and pull requests are built on them.

What a branch really is

  • main is a label pointing at commit c90e5a2.
  • dark-mode is another label pointing at e82b61f. Both lines share their history up to 7b21d94.
  • HEAD points at the branch you are on, dark-mode. Your working folder currently contains dark-mode's version of every file.
  • When you commit, a new commit appears after the one HEAD's branch points at, and that branch label slides forward onto it. The other label stays put.

Think of it like

A transit network. main is the main line. A branch is a new line splitting off at one station and continuing on its own track. HEAD is the red "you are here" dot on the map. Switching branches means changing trains: the scenery (your files) changes to match the line you are on.

Why bother?

  • Safe experiments. Try something on a branch. It works: merge it. It fails: delete the branch. main never noticed.
  • Several things at once. A bug fix on one branch, a new feature on another, without mixing them.
  • Teamwork. Pull requests (Stop 12) are "please merge my branch". On most teams nobody commits to main directly.
  • main stays working. Whatever is on main can be shown, shipped or deployed at any time.

Try it

The branch commands

CommandDoes
git branchLists branches; * marks the one you are on
git branch dark-modeCreates a branch at the current commit (does not switch)
git switch dark-modeSwitches to it: moves HEAD and swaps the files in your folder
git switch -c dark-modeCreates and switches in one step (the one you will actually use)
git switch -Back to the previous branch
git branch -m new-nameRenames the current branch
git branch -d dark-modeDeletes a branch that has been merged (Git refuses if it has unmerged work; -D forces it)

What happens to your files when you switch

Git rewrites your working folder to match the branch you switch to. Files that only exist on the other branch disappear from the folder (they are safe inside .git) and come back when you switch back. That surprises everyone the first time. It is fine.

Uncommitted changes: if they do not clash with the branch you switch to, Git carries them along. If they would be overwritten, Git refuses to switch and tells you which files. Commit them, or put them aside with git stash (Stop 15).

Editors and switching

VS Code notices when Git changes a file and reloads it. Classic Notepad does not: if you still have a file open from the other branch and press Save, you overwrite the new branch's version with the old text. Close files in simple editors before switching branches.

Naming branches

No spaces, lowercase, dashes between words, and a name that says what the branch is for: fix-login-button, add-dark-mode, update-readme. Many teams add a prefix such as feature/ or fix/: fix/login-button.

You create a branch with git branch idea and then commit. Which branch gets the commit?

  • idea
  • The branch you were on, because git branch does not switch
  • Both

git branch name only creates the label. Use git switch -c name to create and move onto it.

What is HEAD?

  • The first commit of the project
  • The newest commit on GitHub
  • A marker for where you are: normally pointing at your current branch

HEAD is "you are here". Switching branches moves it.

After git switch main, a file you created on the other branch vanished from File Explorer. Is it lost?

  • Yes, switching deletes files
  • No, it was committed on the other branch and comes back when you switch there
  • It went to the Recycle Bin

Your folder always shows the branch you are on. Committed files are safe in the repository.

Merging and merge conflicts

Merging brings the work from one branch into another. Most merges happen automatically in a second. Sometimes Git hits a question it cannot answer on its own, a conflict, and asks you. That is not an error; it is a question.

You merge into the branch you are on

The rule people mix up: git merge feature brings feature into your current branch. So first go to the branch that should receive the work, then merge:

git switch main
git merge dark-mode

Two kinds of merge

You do not choose between these; Git picks automatically. (If you always want a merge commit, git merge --no-ff branch forces one.) For a real merge commit Git needs a message and may open your editor with one prewritten, like "Merge branch 'dark-mode'". Save and close to finish.

Practise: one easy merge, one conflict

Anatomy of a conflict

A conflict happens when both branches changed the same lines in different ways. Git writes both versions into the file, fenced by conflict markers:

body {
<<<<<<< HEAD
  background: orange;
=======
  background: palegreen;
>>>>>>> new-colors
  font-family: sans-serif;
}
  • Between <<<<<<< HEAD and =======: your version, from the branch you are on ("current").
  • Between ======= and >>>>>>> new-colors: the version being merged in ("incoming").
  • Everything outside the markers merged cleanly already.

Resolving a conflict, step by step

  1. git status lists every conflicted file under "Unmerged paths".
  2. Open each one. Search for <<<<<<<. VS Code highlights conflicts and offers clickable Accept Current Change, Accept Incoming Change and Accept Both Changes links above each one.
  3. Edit the text into what it should finally be. Keep one side, the other, both, or write something new. Delete every marker line.
  4. Save, then mark the file as resolved: git add style.css
  5. When all files are resolved, finish with git commit (Git suggests the message).

Panicking halfway through? This puts everything back to how it was before the merge:

git merge --abort

Careful

Git lets you git add a file that still contains markers. It will happily commit a broken file. Always search for <<<<<<< before adding.

Fewer conflicts, less pain

  • Merge main into your branch often, so differences stay small.
  • Keep branches short-lived: days, not months.
  • Do not reformat a whole file in the same branch as a real change; that touches every line.
  • Talk to your team when two people need the same file.

You want the work from branch fix to end up on main. What do you run?

  • git switch fix, then git merge main
  • git switch main, then git merge fix
  • git merge main fix

Merge brings the named branch into the branch you are standing on.

What does the section between ======= and >>>>>>> new-colors contain?

  • Your version
  • The version from new-colors, the branch being merged in
  • The version from before both changes

Top half is HEAD (you), bottom half is the incoming branch.

You resolved the conflict in the file. What tells Git it is resolved?

  • Saving the file
  • git add on that file
  • git merge --abort

git add marks the conflict as resolved; then git commit finishes the merge.

GitHub: remotes, push and pull

Until now everything lived on your PC. Now you give the repository a second home on GitHub: an offsite backup, a way to share, and the place where teamwork happens.

1. Create a GitHub account

  1. Go to github.com and click Sign up.
  2. Choose your username carefully. It is public and appears in every URL, like github.com/yourname. Something you would not mind on a CV.
  3. Verify your email address.
  4. Set up two-factor authentication when GitHub asks (it is required for accounts that push code). An authenticator app on your phone works best. Save the recovery codes somewhere safe; lose your phone without them and you lose the account.

2. Create an empty repository on GitHub

  1. Click the + in the top right corner, then New repository.
  2. Name it (for example my-site). Pick Public (anyone can see it) or Private (only you and people you invite).
  3. If you already have the project on your PC, leave "Add a README file", ".gitignore" and "license" all off. Those create a first commit on GitHub that clashes with your own history. (Starting from scratch with nothing local? Then tick README and clone it instead, see below.)
  4. Click Create repository.

GitHub now shows a page of setup instructions. The block you want is titled "...or push an existing repository from the command line":

git remote add origin https://github.com/you/my-site.git
git branch -M main
git push -u origin main
git remote add origin URL
"There is a copy of this repository at this address; let us call it origin." Just a nickname, saved in your repo's settings. Nothing is uploaded yet.
git branch -M main
Renames your current branch to main, in case it was called master. Harmless if it already is main.
git push -u origin main
Uploads main to origin. -u also remembers the link ("upstream"), so from now on a plain git push or git pull knows where to go.

3. Signing in from the terminal

The first push needs to prove it is you. GitHub stopped accepting account passwords for Git in 2021, so pick one of these:

Nothing to set up: it came with Git for Windows. On your first push, a window titled Connect to GitHub appears. Click Sign in with your browser, approve in the browser, done. Windows stores the login securely and never asks again.

Signed in with the wrong account? Open Control Panel → User Accounts → Credential Manager → Windows Credentials, find the entry git:https://github.com, and click Remove. The next push asks again. (Or search the Start menu for "Credential Manager".)

GitHub's own command line tool. It also sets up Git's login, and can create repositories and pull requests from the terminal.

winget install --id GitHub.cli -e
# open a NEW terminal, then:

Answer the questions: GitHub.com, HTTPS, Yes to authenticating Git, Login with a web browser. It shows an 8-character code, opens the browser, you paste the code, done.

Bonus: create the GitHub repository and push, all from your project folder, in one command:

gh repo create my-site --public --source=. --remote=origin --push

An SSH key is a pair of files that proves who you are. Fine, but more steps than the other two, so only use it if you have a reason to.

ssh-keygen -t ed25519 -C "you@example.com"
# press Enter to accept the file location; a passphrase is optional but wise
Get-Content $HOME\.ssh\id_ed25519.pub | Set-Clipboard

That copied your public key. On GitHub: Settings → SSH and GPG keys → New SSH key, paste, save. Test it (type yes the first time):

Hi you! You've successfully authenticated, but GitHub does not provide shell access.

Then use SSH addresses (git@github.com:you/my-site.git) instead of https ones. Never share the file without .pub: that one is private.

How your PC sees GitHub

Your PC keeps a remote-tracking branch called origin/main: a bookmark of where main was on GitHub the last time you talked to it. It only updates when you run fetch, pull or push, which is why git status can say "up to date" while a teammate has pushed something new. Run git fetch and it knows.

Practise: push, get rejected, pull, push

The three sync commands

A rejected push ("Updates were rejected because the remote contains work that you do not have locally") is the most common GitHub message there is. It means a teammate pushed first. Run git pull, resolve any conflict, then git push again.

Cloning: starting from GitHub instead

When the repository already exists on GitHub (someone else's project, or yours on a new PC), you do not init; you clone. On the repository's GitHub page, click the green Code button and copy the HTTPS address. Then:

cd ~\projects
git clone https://github.com/you/my-site.git
cd my-site

Clone creates a new folder named after the repository, with the full history, origin already set, and main already linked to origin/main. The classic beginner slip is forgetting the cd my-site afterwards and running Git in the parent folder.

The daily loop, with GitHub

Your push is rejected because "the remote contains work that you do not have locally". What now?

Someone else pushed first. Bring their work in with pull, then your push can go on top.

You created the GitHub repository with a README, but you already had a local project with commits. What happens on push?

That is why you leave README, .gitignore and license unticked when pushing an existing project.

Which command is always safe and never changes your files?

Pull requests

A pull request (PR) says: "I made changes on a branch. Please look at them, and if they are good, merge them into main." It is where review, discussion and automatic checks happen before anything touches main.

Why teams (and even solo developers) use them

  • A second pair of eyes. A teammate reads the change before it lands. Bugs get caught while they are cheap.
  • Automatic checks. Tests and builds run on every PR and show a green or red mark.
  • A record of why. Months later, the PR page still explains what changed and why, with the whole discussion.
  • main stays clean. Nothing reaches it without passing through a PR.

Good pull request manners

  • One topic per PR. Small PRs get reviewed fast; huge ones get skimmed or ignored.
  • Title a stranger understands. Description: what, why, and how to test it. Screenshots for visual changes.
  • Link the issue: Closes #3 closes it automatically on merge.
  • Not finished but want feedback? Open a draft pull request.
  • Review comments are about the code, not about you. Answer each one, push fixes, say thanks.

  • Commit the fixes on the same branch and push; the PR updates itself
  • Merge anyway

  • Nothing, your PC updates automatically
  • git switch main, git pull, then git branch -d fix-typo
  • git push --force

Forks: contributing to other people's projects

You cannot push to a repository you do not own. That would be chaos. Instead you make your own copy on GitHub, a fork, change that, and send a pull request back to the original. This is how all of open source works.

Three copies of one project

Step by step

  1. On the project's GitHub page, click Fork (top right), then Create fork. You now own you/cool-game.

.gitignore: files Git should never see

Some files must stay out of your repository: passwords and keys, gigantic folders of downloaded packages, build output, and Windows' own junk files. A plain text file called .gitignore lists them, and Git then acts as if they do not exist.

What typically goes in it

Secrets

.env files, API keys, *.key, passwords. The number one thing to never commit.

Things you can regenerate

node_modules/, dist/, build/, __pycache__/, bin/, obj/. Huge, and rebuilt by a command anyway.

Windows and editor junk

Thumbs.db, desktop.ini, *.log, .vs/, personal editor settings.

Creating the file on Windows

The name is literally .gitignore: it starts with a dot and has no extension. Windows makes that oddly fiddly:

  • Easiest, in the terminal: ni .gitignore then notepad .gitignore
  • VS Code: New File, name it .gitignore. Works as expected.
  • Notepad's Save dialog: set "Save as type" to All files (*.*) before typing the name. Otherwise Notepad quietly saves .gitignore.txt, which Git ignores completely.

Win 11 File Explorer accepts a name starting with a dot. Turn on View → Show → File name extensions so you can see whether a sneaky .txt got attached.

Win 10 Older Windows 10 builds refuse a name that starts with a dot ("You must type a file name"). Trick: type .gitignore. with an extra dot at the end; Windows removes the trailing dot for you. Also tick View → File name extensions to spot a sneaky .txt.

Put it in the top folder of your project (next to .git) and commit it like any other file, so your teammates get the same rules.

Pattern rules

LineIgnores
secret.txtAny file or folder named secret.txt, in any folder
*.logEvery file ending in .log, anywhere
build/Every folder named build, with everything inside (trailing slash = folders only)
/todo.txttodo.txt only in the top folder (leading slash = anchored to the project root)
docs/*.pdfPDFs directly inside docs
**/temptemp at any depth (same as plain temp)
!keep.logException: do not ignore keep.log, even though *.log matched it
# commentNothing; a note for humans

Rules are read top to bottom and the last matching rule wins. One catch: if a whole folder is ignored, a ! rule cannot bring back a file inside it.

Try it: a live .gitignore tester

Edit the rules or the file list; the verdict updates as you type. Paths use forward slashes, the way Git writes them. Matching ignores upper and lower case, like Git on Windows does.

"I added it to .gitignore, but Git still tracks it"

.gitignore only affects files Git is not tracking yet. If the file was committed before, tell Git to stop tracking it (the file stays on your disk), then commit:

git rm --cached .env
git commit -m "Stop tracking .env"

For a whole folder: git rm -r --cached node_modules. And to find out which rule is ignoring a file:

git check-ignore -v debug.log

Committed a password?

Removing the file in a new commit is not enough: it is still in the history, and if you pushed, it is on GitHub. Change the password or revoke the key first, immediately. That is the real fix. Scrubbing history afterwards is possible (the tool is git filter-repo) but it is advanced surgery, and anything already public should be treated as leaked.

Starting points

  • When creating a repository on GitHub, the Add .gitignore dropdown offers ready-made templates per language (Node, Python, VisualStudio and so on).
  • GitHub's collection of templates lives in the github/gitignore repository.
  • For junk that follows you everywhere (Thumbs.db, desktop.ini), make a personal global ignore file once: 
    notepad $HOME\.gitignore_global
git config --global core.excludesFile "$HOME\.gitignore_global"

Which line ignores every .log file except important.log?

  • *.log important.log
  • *.log on one line, then !important.log below it
  • !*.log

Last matching rule wins, so the exception has to come after the general rule.

You added .env to .gitignore, but git status still shows it as modified. Why?

  • .gitignore only works after a restart
  • It was already tracked; use git rm --cached .env and commit
  • The file name is case-sensitive

Ignore rules only apply to untracked files. Stop tracking it first.

  • The file is really called .gitignore.txt
  • Notepad cannot write plain text
  • Rules only work on GitHub

The toolbox: stash, tags, rebase, reflog

Four tools you will not use every day, but you will be very glad to know about on the day you need them. Plus a sandbox at the end where anything goes.

Stash: "hold that thought"

You are halfway through something messy and need to switch branches right now, for an urgent fix. You do not want to commit half-finished work. Stash puts your uncommitted changes on a shelf and gives you a clean folder; later you take them back off the shelf.

CommandDoes
git stashShelve changes to tracked files; folder goes back to the last commit
git stash -uShelve new (untracked) files too
git stash push -m "redesign"Shelve with a label
git stash listShow the shelf
git stash popTake the newest entry back and remove it from the shelf
git stash applyTake it back but keep a copy on the shelf
git stash dropThrow away the newest entry

PowerShell and stash@{1}

Older entries are named stash@{1}, stash@{2}... PowerShell treats @{ } as its own syntax and mangles it. Wrap the name in single quotes: git stash apply 'stash@{1}'

Stash is for short interruptions. Anything that lives longer than an afternoon belongs in a commit on a branch, where it has a name and a message.

Tags: permanent labels for releases

A tag is like a branch that never moves. You stick it on a commit to mark it forever: "this is version 1.0".

# annotated tag (with author, date and a message), the recommended kind
git tag -a v1.0 -m "First public release"
# list tags
git tag
# tags are not pushed automatically:
git push origin v1.0

On GitHub, Releases are built on tags: pick a tag, write release notes, attach downloadable files.

Rebase: replaying your work on a new base

Merge ties two lines together with a merge commit. Rebase does something different: it lifts your branch's commits off and replays them, one by one, on top of another branch. The result is a straight line, as if you had started your work after the latest main.

C' and D' are new commits with new IDs (the originals are left behind). That is the whole catch, and it leads to the golden rule:

The golden rule of rebasing

Never rebase commits that other people already have, such as anything on main or a branch someone else uses. Rebase your own, unpushed (or unshared) work only. Breaking this rule forces everyone else to untangle duplicate commits.

  • git pull --rebase replays your local commits on top of what you downloaded instead of making a merge commit. Many people like it for keeping history tidy.
  • git rebase -i HEAD~3 ("interactive") opens your editor with the last three commits, so you can reorder, reword or squash them before pushing. Powerful; practise on a throwaway repository first.
  • Rebase can hit conflicts too. Fix the file, git add it, git rebase --continue. Or bail out with git rebase --abort.

Reflog: the safety net under everything

Deleted a branch you needed? Did a reset --hard too far? The reflog is Git's private diary of every place HEAD has been, kept for about 90 days by default. Commits are almost never truly gone while it remembers them.

git reflog
e82b61f (HEAD -> main) HEAD@{0}: reset: moving to HEAD~2
4d7aa31 HEAD@{1}: commit: Add contact page
c90e5a2 HEAD@{2}: commit: Tweak colors

Found the commit you want back? Put a branch on it, or jump straight back:

git branch rescued 4d7aa31
# or undo the reset itself (quotes needed in PowerShell):
git reset --hard 'HEAD@{1}'

What the reflog cannot save: changes you never committed. One more reason to commit early and often.

Detached HEAD: not as scary as it sounds

Normally HEAD points at a branch. If you switch to a commit directly (git switch --detach 7b21d94, or git checkout 7b21d94), HEAD points at the commit itself: detached HEAD. Perfect for looking at an old version. The risk: commits you make there belong to no branch and are easy to lose.

  • Just looking? Go back with git switch - or git switch main.
  • Made commits you want to keep? Give them a branch first: git switch -c keep-this.

Two more worth knowing

git cherry-pick a1b2c3d
Copies one single commit from another branch onto yours. Handy for grabbing one bug fix without merging a whole branch.
git blame index.html
Shows, line by line, which commit and person last changed each line. Despite the name, mostly used to find out why a line exists.

The sandbox

No instructions, no checklist. A repository with a feature branch, a GitHub remote and a few commits. Try git switch feature then git rebase main and watch the map redraw; tag something; reset too far and rescue it with the reflog; detach HEAD and wander around. "Start over" resets it.

You are mid-change and must switch branches for an urgent fix. Quickest safe move?

  • git reset --hard
  • git stash, switch and fix, switch back, git stash pop
  • Delete the changed files

Stash parks the changes without a commit and gives them back later.

When is it fine to rebase?

  • Always
  • Only on main
  • On your own commits that nobody else has yet

Rebase creates new commits. Rewriting commits others have causes duplicate history.

You ran git reset --hard HEAD~3 by mistake. Is the work gone?

  • Yes, forever
  • The commits can be found with git reflog and restored
  • Only GitHub support can restore it

The reflog remembers where HEAD was. Committed work comes back; only uncommitted edits are lost.

Windows gotchas and fixes

Git grew up on Linux. On Windows it works very well, but a handful of differences bite beginners again and again. Here is every one of them, with the fix.

1. Line endings: CRLF versus LF

Every line in a text file ends with invisible characters. Windows uses two, carriage return plus line feed (CRLF); macOS and Linux use just line feed (LF). Without care, a Mac user and a Windows user editing the same file make Git think every single line changed. Git's core.autocrlf setting converts for you. Click through the options:

This is also where the message warning: in the working copy of 'index.html', LF will be replaced by CRLF the next time Git touches it comes from. It is informational. Nothing is wrong.

For a team project, the robust fix is a .gitattributes file in the project's top folder, committed like any other file. It makes the rules part of the repository, so everyone gets the same behaviour whatever their personal settings:

# let Git normalise all text files
* text=auto
# shell scripts must keep LF, even on Windows
*.sh text eol=lf
# Windows batch files must keep CRLF
*.bat text eol=crlf
*.cmd text eol=crlf

2. Upper and lower case in file names

To Windows, README.md and readme.md are the same file. To Git (and to Linux servers, and GitHub), they are different. Consequences:

  • Renaming readme.md to README.md in File Explorer changes nothing as far as Git is concerned. Use Git to rename it: git mv readme.md README.md, then commit.
  • A repository made on Linux containing both Photo.jpg and photo.jpg cannot be checked out properly on Windows. Rare, but confusing when it happens.

3. "Filename too long"

Windows traditionally limits paths to 260 characters, and deep folders (hello, node_modules) exceed that. Fix it on both sides:

git config --global core.longpaths true

Then let Windows itself allow long paths. Open PowerShell as administrator (right-click Start, pick Terminal (Admin)Windows PowerShell (Admin)) and run:

New-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Control\FileSystem" -Name "LongPathsEnabled" -Value 1 -PropertyType DWORD -Force

Restart your terminal and editors afterwards. (Only needed if you actually hit the error.)

4. OneDrive and Git do not mix

OneDrive often syncs your Desktop and Documents folders without asking. A repository inside a synced folder means two programs fighting over the thousands of small files in .git: sync conflicts, "file in use" errors, sometimes a corrupted repository.

Fix

Keep repositories in a folder OneDrive does not touch, such as C:\Users\you\projects or C:\dev. Your backup is GitHub; that is what push is for.

Win 11 For heavy projects, Windows 11 offers a Dev Drive (Settings → System → Storage → Advanced storage settings → Disks & volumes → Create dev drive): a separate volume tuned for developer workloads where Microsoft Defender scans in a lighter mode, which makes Git and package installs noticeably faster. Optional.

Win 10 If Git feels slow in huge repositories, antivirus scanning of the many small files is a common cause. Recent Git for Windows versions are already well tuned; keeping Git updated helps most.

7. Signed in as the wrong GitHub account

Git Credential Manager remembers one login per site. To switch: open Credential Manager (search the Start menu), Windows Credentials, remove git:https://github.com, then push again and sign in fresh. A "403" or "Permission denied" on push usually means this, or that you are pushing to a repository you do not have access to.

8. "Running scripts is disabled on this system"

This is PowerShell refusing to run .ps1 script files, which matters for add-ons such as posh-git or some npm tools (plain git is unaffected). Windows blocks scripts by default. Allowing your own local scripts for your user only is the common, reasonable setting:

Set-ExecutionPolicy -Scope CurrentUser RemoteSigned

Win 11 The same switch lives in Settings → System → For developers (named Advanced on the newest builds), in the PowerShell section.

Win 10 The same switch exists in Settings → Update & Security → For developers, in the PowerShell section.

Final exam

Twelve questions from across the whole line. No pressure: every answer comes with an explanation, and the stop number to revisit if it did not stick.

1. Git versus GitHub: which statement is true?

  • GitHub is required to use Git
  • Git runs on your PC; GitHub hosts copies of repositories online
  • They are the same thing

Stop 1. Git works offline; GitHub is a website built around it.

2. Right after installing Git, PowerShell says "git is not recognized". First thing to try?

  • Reinstall Windows
  • Open a new terminal window
  • Run git as administrator

Stop 3. Terminals only see programs that existed when they started.

3. What does git add index.html do?

  • Uploads index.html to GitHub
  • Copies the current version of index.html into the staging area
  • Creates a new file

Stop 5. Staging decides what goes into the next commit.

4. git status lists a file in red under "Untracked files". Meaning?

  • Git sees the file but has never been told to track it
  • The file is corrupted
  • The file is ignored

Stop 5. git add it to start tracking.

5. You committed with a typo in the message and have not pushed. Fix?

  • git revert HEAD
  • git commit --amend -m "Correct message"
  • Delete the .git folder

Stop 8. Amend replaces the last commit; fine because nobody else has it yet.

6. A bad commit is already on GitHub and teammates pulled it. Fix?

  • git reset --hard and git push --force
  • git revert it, then push
  • Ask GitHub support

Stop 8. Never rewrite shared history; add an undoing commit.

7. Which command creates a branch and switches to it?

  • git branch -d name
  • git switch -c name
  • git merge name

Stop 9. git branch name only creates; -c creates and switches.

8. To get branch feature into main, you...

  • git switch feature, then git merge main
  • git switch main, then git merge feature
  • git push feature main

Stop 10. You merge into the branch you are on.

9. After fixing a conflicted file, how do you mark it resolved?

  • Save it
  • git add the file, then git commit
  • git merge --abort

Stop 10. git add marks it resolved; the commit finishes the merge.

10. Your push is rejected: "the remote contains work that you do not have locally". Next?

  • git push --force
  • git pull, then git push
  • Create a new repository

Stop 11. Someone pushed first; integrate their work, then push.

11. You want to contribute to a project you cannot push to. The workflow?

  • Email your files to the owner
  • Fork, clone your fork, branch, push to your fork, open a pull request
  • Clone the original and push with --force

Stops 12 and 13.

12. You added .env to .gitignore but Git still tracks it. Why, and the fix?

  • .gitignore needs a restart
  • It was already tracked; git rm --cached .env and commit
  • Rename it to .ENV

Stop 14. Ignore rules only apply to untracked files. (And if it held a real secret: change that secret.)

Where to go from here

  • Put something real on GitHub. Notes, a small website, dotfiles, a school project. Use a branch and a pull request even when working alone; it builds the habit.
  • Host a website for free. GitHub Pages publishes a repository of HTML files as a live site (repository Settings → Pages).
  • Make a first open source contribution. Search GitHub for the label good first issue.
  • Go deeper. The book "Pro Git" is free on git-scm.com/book, and GitHub Skills (skills.github.com) has short hands-on courses that run inside real repositories.
  • Use your editor's Git panel. Now that you know what staging, commits and branches are, VS Code's Source Control view will make total sense.

And when something goes wrong: git status, read it slowly, and remember that committed work is almost never truly lost.
